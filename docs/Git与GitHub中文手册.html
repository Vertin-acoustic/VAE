01

先把 Git 与 GitHub 分开

Git 管理版本；GitHub 托管仓库，并提供讨论、协作与自动化。

ON YOUR COMPUTER

Git · 本地版本工具

记录文件的版本与变化。即使没有网络，你也能查看差异、创建提交、建立分支。隐藏目录 .git 保存版本数据库等元数据。

ON GITHUB.COM

GitHub · 远程协作平台

保存你推送的 Git 历史，展示文件，管理 Issue、PR、自动检查与权限。你现在的远程仓库是 Vertin-acoustic / VAE ↗。

容易混淆准确理解你的例子
Repository / Repo · 仓库项目文件及其版本历史；本地与远程各有一份。VAE 目录是本地工作位置，GitHub 的 VAE 是远程仓库。
Save / Commit / Push保存文件 → 记录本地版本 → 同步到远程，三个不同动作。Ctrl+S 不会自动 commit；commit 不会自动 push。
main / origin / origin/mainmain 是本地分支；origin 是远程地址别名；origin/main 是本地保存的远程 main 状态。origin/main 不是不断自动刷新的云端直播，需要 fetch 等操作更新。
HEAD · 当前检出位置通常指向你当前所在分支及其最新提交。在 main 工作时，HEAD 通常跟随 main。
Branch · 分支一条可继续前进的开发历史引用，不是另复制一整个项目目录。可以在 lesson-01 分支试验，再合并回 main。
Git 身份 / GitHub 登录user.name 和 user.email 标注提交作者；登录凭据负责远程访问。设置 Vertin-acoustic 这个名字并不等于已经登录 GitHub。
这次的真实记录：你的本地历史已有 e71100f（第 0 课反馈），之前是 f26cdf1（课程材料）、fda2367（论文）。2026-10-08 检查时工作区干净、本地 main 与保存的 origin/main 相同；结合你的成功反馈和网页截图，首次上传记为完成。手册里的后续示例不是已替你执行的操作。

03

每次学习后的保存流程

在 PyCharm 的 Terminal（终端）里执行；不要在 Python Console 或 Notebook 代码格里执行这些命令。

Set-Location -LiteralPath 'D:\AAA文献库\A仿生通信\生成式\VAE'
git status
git diff -- docs/学习记录.md
git add -- docs/学习记录.md 计划.md
git diff --cached --stat
git commit -m "Record learning progress"
git push origin main
git status
动作为什么做看到什么
先保存文件Git 读取磁盘内容；未保存的编辑不在里面。Notebook 若保留输出，先确认代码与输出对应。
status / diff先看这次改了哪些文件、具体改了什么。新文件先在 status 里出现；首次 add 前通常不在普通 diff 里。
add / diff --cached选择此次提交的范围，再看已经选中的内容。文件进入 Changes to be committed。
commit保存一个可以用编号找到的本地版本。例如出现新的 7 位短编号和修改摘要。
push把远程缺少的提交推送出去。刷新 GitHub Code 页，确认最新提交和文件。
上面的例子假设只修改了学习记录和计划。如果还改了 Notebook，就把对应路径加到 git add -- 后。暂存后继续修改同一个文件，需要再次 add。git push 不会替你提交尚未 commit 的文件。
只修改网页上的 README 之后，本机怎么办？

网页编辑并提交后，远程历史变了。本机先确认没有未保存工作，再运行 git fetch origin 查看更新，在 main 上使用 git pull --ff-only origin main 同步。若提示分叉，先检查历史，不强制覆盖。

04

命令速查：知道何时用，才记得牢

所有示例默认位于 VAE 仓库根目录，另有说明的除外。先看用途，再复制执行。

常用官方语法 ↗

git status

查看当前状态

git status
git status -sb

随时看分支、暂存与未暂存文件。-s 为简短形式，-b 显示分支。

不会下载远程最新状态；“clean”也不表示代码正确。

常用官方语法 ↗

git diff

查看尚未暂存的修改

git diff -- docs/学习记录.md

比较工作区与暂存区。-- 后是文件路径，减少与选项混淆。

若已经 add，普通 diff 可能为空；改看 --cached。

常用官方语法 ↗

git add

选入暂存区

git add -- docs/学习记录.md 计划.md

暂存指定路径的新增、修改或删除，作为本次提交内容。

add 是选择快照，不是上传。git add . 范围较大，先看 status。

常用官方语法 ↗

git diff --cached

检查准备提交的内容

git diff --cached
git diff --cached --stat

--cached 比较暂存区与 HEAD；--stat 只看每个文件的改动摘要。

Notebook 的 JSON 差异可能较长，可配合 PyCharm 的 Notebook 对比。

常用官方语法 ↗

git commit -m

建立本地版本

git commit -m "Explain notebook execution order"

把暂存内容记录为提交；-m 指定说明，建议写清改动目的。

没有暂存改动就不会产生普通提交；它不是云端备份。

常用官方语法 ↗

git push

上传提交

git push origin main

把本地 main 的提交推送到 origin 的 main。

这里的 main 指本地分支，不是任意当前分支；示例在 main 上使用。

常用官方语法 ↗

git log

查看历史

git log -5 --oneline
git log --oneline --graph --decorate --all

第一条显示最近 5 次；第二条看所有分支的提交图。

--oneline 一行一条，--graph 画图，--decorate 显示分支标签。分页器按 q 退出。

查阅官方语法 ↗

git show

查看某一次提交

git show --stat e71100f
git show e71100f -- docs/学习记录.md

用你已有的提交号查看其摘要，或限定一个文件的变化。

只查看，不会把工作区变回旧版本。

查阅官方语法 ↗

git remote -v

确认上传地址

git remote -v

显示远程别名和 fetch / push 地址。

origin 只是名字，不是 GitHub 用户名，也不是分支。

查阅官方语法 ↗

git fetch

获取远程历史

git fetch origin

更新远程跟踪引用和对象，先了解云端变化。

普通 fetch 不把远程改动直接合并进当前工作文件。

查阅官方语法 ↗

git pull --ff-only

同步到远程较新的版本

git switch main
git pull --ff-only origin main

在 main、工作区干净时用。先获取，再仅允许快进，把本地分支移到远程较新的提交。

--ff-only 遇到分叉会停止，不会偷偷创建合并提交；远程有更新时再用。

查阅官方语法 ↗

git diff 分支比较

检查远程与本地差异

git fetch origin
git diff --stat main origin/main

fetch 后比较两个分支当前快照有哪些文件不同。

两端快照相同不代表提交历史完全相同，可配合 log 图。

分支官方语法 ↗

git branch

列出分支与跟踪关系

git branch
git branch -vv

星号标出当前分支；-vv 显示对应的上游及已知同步情况。

它显示的远程情况基于本地已有信息。

分支官方语法 ↗

git switch -c

创建并切换到实验分支

git switch -c lesson-01

从当前提交创建 lesson-01，然后切过去开展新实验。

先完成或安置手头的改动；这不会自动在 GitHub 创建分支。

分支官方语法 ↗

git switch

切换回已有分支

git switch main

把当前工作位置切换到 main。

未提交改动有时会随你过去，有时会阻止切换；先看 status。

分支官方语法 ↗

git push -u

首次上传新分支

git push -u origin lesson-01

推送 lesson-01 并设置它的上游。以后在该分支通常可直接 git push。

-u 是 --set-upstream 的简写；你现有 main 已有上游，不必重复设置。

分支官方语法 ↗

git merge

在本地合并另一分支

git switch main
git merge lesson-01

将 lesson-01 的历史合入当前 main；可能快进，也可能产生合并提交。

这是本地合并路径。若已经通过 GitHub PR 合并，回来 pull 同步即可，不用再照做。

分支官方语法 ↗

git branch -d

删除已完成的本地分支

git branch -d lesson-01

确认合并完成、当前不在 lesson-01 后，删除本地分支名。

不会删除 GitHub 分支；若因未合并被拒绝，先核对，不改用 -D 硬删。

看清作用官方语法 ↗

git restore --staged

撤销暂存，保留文件修改

git restore --staged -- docs/学习记录.md

刚才选错了文件，先从本次待提交内容中撤下。

工作区中的编辑还在；本例适用于已有 HEAD 的当前仓库。

看清作用官方语法 ↗

git restore

丢弃指定文件未暂存的改动

git restore -- docs/学习记录.md

确认不需要该文件的未暂存编辑时，将工作文件恢复到暂存区版本。

这会覆盖编辑内容；先用 diff 查看。有暂存改动时，恢复目标不一定是上次提交。

看清作用官方语法 ↗

git revert

用新提交抵消一个旧提交

git revert --no-edit abc1234

示意：先从 git log 找到要撤销的普通提交，替换 abc1234；它创建反向修改的新提交。

abc1234 是占位示例，不能直接照抄。可能发生冲突；合并提交需另行处理。

看清作用官方语法 ↗

git stash

临时收起尚未提交的工作

git stash push -u -m "Pause lesson notes"
git stash list
git stash pop

临时离开当前任务时使用；-u 连未跟踪文件一起收起；pop 尝试恢复最近一份。

忽略文件不含在 -u 中。pop 可能冲突；stash 是本地临时存放，不会随 push 上传。

看清作用官方语法 ↗

git check-ignore

查为什么文件没有出现

git check-ignore -v outputs/environment_check.json

显示命中的忽略规则及来源，适合检查 outputs、缓存或模型文件。

没有命中时可能无输出并返回非零；不等于仓库损坏。

按需官方语法 ↗

git clone

在另一台电脑下载完整仓库

git clone https://github.com/Vertin-acoustic/VAE.git

在你选好的父目录执行，创建 VAE 子目录并下载历史。

当前已有 VAE 仓库不要在里面再 clone 自己。ZIP 通常没有 Git 历史。

按需官方语法 ↗

git init

给全新本地目录建立仓库

git init -b main

仅用于一个尚无 Git 历史的新项目。-b 指定初始分支名。

当前 VAE 已初始化；不需要每次保存时重新 init。

按需官方语法 ↗

git config --local

设置本仓库作者身份

git config --local user.name "Vertin-acoustic"
git config --local user.email "1434571123@qq.com"

--local 只影响当前仓库；不加值时可查询对应设置。

这两项已配置；它们不是 GitHub 登录凭据。

按需官方语法 ↗

git remote add

登记远程仓库地址

git remote add origin https://github.com/Vertin-acoustic/VAE.git

给已存在的本地仓库添加 origin 地址别名。

当前已登记；重复执行会提示 origin already exists，先用 remote -v 看。

按需官方语法 ↗

git tag

给稳定版本起一个固定名字

git tag -a lesson-00 -m "Lesson 00 milestone"
git push origin lesson-00

可选：给当前提交做带说明的标签，并显式上传该标签。

Tag 像里程碑标记；分支则会随新提交继续移动。标签不会因普通 main 推送而必然上传。

按需官方语法 ↗

git mv

重命名并暂存路径变化

git mv docs/old-note.md docs/new-note.md

路径仅为示例，old-note.md 必须已存在且被跟踪。用于文件改名。

Git 对历史重命名的识别依赖相似度；不是给文件分配永久不变的名字。

按需官方语法 ↗

git rm --cached

停止跟踪，保留本地文件

git rm --cached -- checkpoints/model.pt

仅用于误跟踪的示例模型文件；再把它加入 .gitignore 并提交。

这只影响之后的快照，不会从旧历史里抹去该文件。

-- 常用来表示“后面是文件路径”；-m 是 message（说明）；-u 在 push 与 stash 中含义不同，必须结合命令理解。示例中的引号使用英文半角引号。

05

读懂终端英文与 diff

不用逐词硬译。先判断：这是状态说明、成功信息，还是需要处理的问题？

终端原文中文含义下一步
On branch main当前位于 main 分支。确认是自己想操作的分支。
Changes not staged for commit有修改，但尚未选入下次提交。diff 看完后，对需要的文件 add。
Changes to be committed这些修改已暂存，将进入下一次提交。用 diff --cached 检查。
Untracked filesGit 还没有跟踪的新文件。需要保存就 add，不需要跟踪就设忽略规则。
nothing to commit, working tree clean没有待提交的文件改动。不表示已经上传；继续看 ahead / behind。
ahead of origin/main by 1 commit比本地记录的远程分支多 1 个提交。通常需要 push；必要时先 fetch 确认远程现状。
behind / diverged落后 / 双方都有对方没有的提交。落后可在合适条件下快进；分叉先看 log 图。
Everything up-to-date这次推送所涉及的引用没有新的内容可上传。文件改了仍出现它？检查是否先 add 和 commit。
rejected / non-fast-forward远程拒绝了这次非快进更新。先 fetch 查看双方历史，再处理合并；不要直接强推。
Authentication failed / Permission denied身份认证失败 / 权限不足。确认登录账户、仓库权限和凭据；改 user.name 不能代替登录。
Could not connect / Connection timed out无法连接 / 网络超时。检查网络和当前代理；不需要重新初始化仓库。
not a git repository当前目录不在一个 Git 仓库内。用 Set-Location 进入正确的 VAE 目录。
LF will be replaced by CRLF文本换行格式可能被转换。通常是换行提示，不等于 commit 失败；看命令最终结果。
CONFLICT / Automatic merge failed合并冲突 / 自动合并未完成。查看冲突文件并确认内容；不要盲目接受全部 ours 或 theirs。

短格式中的两个位置

 M docs/学习记录.md
M  README.md
MM notebooks/00_运行第一段代码.ipynb
?? docs/new-note.md

第一列描述暂存区相对 HEAD的变化，第二列描述工作区相对暂存区的变化： M 是未暂存修改，M 是已暂存修改，MM 是暂存后又修改。?? 是未跟踪文件。

diff 的 + 与 −

-whistle_count = 3
+whistle_count = 5

这表示旧行删除、新行加入；行前符号是差异标记，不是需要粘进 Python 的代码。它记录文本怎么变，不会判断你的实验结论是否正确。

PULL REQUESTS

提出改动，请求审查与合并

Pull request，简称 PR，可理解为“合并请求”。你提出将某个分支的改动合入另一个分支，大家可以先查看差异、讨论、检查，再决定合并。

别被 pull 这个单词带偏：git pull 是本机获取并整合远程更新；Pull request 是 GitHub 上的审查与合并流程。直接向 main 推送成功，并不会自动创建 PR。
界面英文中文解释你的例子
New pull request / Compare & pull request新建 PR / 比较并创建 PR。上传 lesson-01 后，提议将其合并进 main。
base / compare（或 head）目标分支 / 提供改动的来源分支。base: main，compare: lesson-01。方向是 lesson-01 → main。
Conversation讨论：说明、时间线、评论和审查。写清为什么修改、改了什么、怎么验证。
Commits这个 PR 中的提交记录。可能有多个本地 commit，不限一个。
Checks自动检查。未来可检查 Python 代码或 Notebook 格式。没有配置时可能没有检查。
Files changed文件差异。逐行查看增加和删除；可以针对某行评论。
Findings（若显示）自动检查或审查发现的问题。内容取决于仓库启用的功能。
Reviewers / Assignees审查人 / 负责人，常在右侧。前者帮你审查，后者负责跟进工作。
Labels / Projects / Milestone / Development标签 / 看板 / 里程碑 / 关联开发事项。可将 PR 与学习 Issue 关联。
Draft / Ready for review草稿 / 已准备好审查。还没写完先 Draft；草稿 PR 不能直接合并。
Approve / Request changes / Comment批准 / 请求修改 / 评论。Review 是审查行为，不等于点击 Merge。
Merge pull request执行合并。把来源分支改动纳入目标分支；需要权限和满足仓库规则。
Close pull request / Merged关闭 PR / 已合并。关闭不一定合并；Merged 明确表示已合并。

三种合并方式

方式发生什么初学者怎样理解
Create a merge commit在相应模式下保留原分支提交，并增加合并节点。能看见两条历史合流。
Squash and merge把 PR 的改动汇总为目标分支上的一个新提交。适合把多次“修修补补”整理成一次清楚的变化。
Rebase and merge把来源提交依次重新放到目标分支之上，不加普通合并节点。历史较直线，提交标识会改变；暂时只需认识。

ACTIONS

自动执行事先写好的工作流

Actions 可以在 push、PR 或手动触发时执行检查。例子：你上传课程代码后，自动检查是否有语法错误。Actions 的绿色状态表示所配置检查通过，不代表所有学习任务都正确。

英文中文与位置具体含义
All workflows所有工作流，通常位于左侧。看仓库各工作流的运行记录。
Workflow / New workflow工作流 / 新建工作流。自动化规则通常写在 .github/workflows/ 下的 YAML 文件里。
Workflow 名称列表左侧各工作流入口。点击某个名字，只看该流程的历史。
Run / Workflow run一次运行。同一工作流每次触发，产生新的运行记录。
Event / Branch / Actor / Status触发事件 / 分支 / 触发者 / 状态。用于筛选究竟是谁、在哪个分支触发了运行。
Queued / In progress / Success / Failure / Cancelled / Skipped排队 / 执行中 / 成功 / 失败 / 已取消 / 已跳过。失败时点进去看日志，别只看红叉。
Job / Step任务 / 步骤。一个工作流可有多个 Job；每个 Job 内有若干 Step。
Runner执行任务的机器。GitHub 托管机器或自托管机器；不是自动使用你笔记本的显卡。
Summary / Logs / Artifacts摘要 / 日志 / 产物。产物例如测试报告，可下载，不等于提交进仓库。
Run workflow手动运行工作流。只有工作流支持手动触发且权限合适时才出现。
Re-run jobs / Cancel workflow重新运行任务 / 取消本次流程。重跑也会实际使用执行资源。
Caches / Runners / Management（可能出现）缓存 / 执行机器 / 管理。属于辅助管理入口，是否出现取决于权限与界面。
你目前的课程不需要先开启 CI，也不用在 Actions 里训练 VAE。先认识“上传代码”和“让服务器自动运行代码”是两件事。

PROJECTS

把学习任务组织成表格或看板

Projects 可将 Issue、PR 和草稿任务放在一起安排。项目通常归用户或组织所有，再关联到仓库；它不是硬盘里的 PyCharm 项目文件夹。

英文中文含义学习场景

Table / Board / Roadmap表格 / 看板 / 时间路线图。用表格看字段，用看板看待办与完成，用路线图看时间。
View / Filter / Group by / Sort视图 / 筛选 / 分组 / 排序。一个项目可保存多种观察方式，不是复制多份任务。
Todo / In progress / Done待做 / 进行中 / 已完成。例如“解释重参数化”从 Todo 移到 In progress。
Item / Draft issue / Add item条目 / 草稿任务 / 添加条目。草稿不一定已经成为仓库中的正式 Issue。
Fields / Priority / Iteration字段 / 优先级 / 迭代周期。可按课次、计划时间和重要程度整理。
Workflows / Insights / Settings项目内自动化 / 统计 / 设置。这些是该 Project 的功能，不完全等同于仓库 Actions、Insights、Settings。

看仓库活动与统计

Insights 可译为“洞察”，这里直接理解成统计与活动分析。它帮助看谁提交、何时活跃、是否有人访问；不负责保存文件。

把命令放回真实场景

以你现在的学习方式为主；分支、PR 和撤回在需要时再用。

场景 A：把这份手册也上传到仓库

我创建手册和配套截图，并更新本课文档；提交和上传继续由你练习。先确认 status 中确实只有这些相关变化，再执行：

git status
git add -- docs/Git与GitHub中文手册.html docs/assets/git-guide README.md 计划.md docs/学习记录.md docs/Git操作记录.md
git diff --cached --stat
git commit -m "Add Chinese Git and GitHub handbook"
git push origin main

HTML 使用相对路径引用 docs/assets/git-guide 中的三张截图，这个文件夹要一起上传。网页可离线阅读；官方参考链接与仓库链接需要网络。GitHub 文件页查看 HTML 源码是正常现象，本地浏览器打开才是完整交互界面。

场景 B：为下一课开一个分支，并通过 PR 合并

先保证 main 工作区干净、已同步，再创建新分支：

git switch main
git pull --ff-only origin main
git switch -c lesson-01

编辑实际课程文件并保存，检查后 add 和 commit，然后：

git push -u origin lesson-01

网页点 Pull requests → New pull request，选 base: main、compare: lesson-01，查看 Files changed 后创建 PR。准备好时审查并合并。网页合并后，本机：

git switch main
git pull --ff-only origin main

分支解决“并行试验”，PR 解决“审查与合并”。你独自学习时可以直接使用 main；此例是逐步学习协作的可选路线。

场景 C：误把文件加进暂存区

只是 add 错了，不想丢掉文字：

git restore --staged -- docs/学习记录.md
git status

文件内容保留，只改变这次提交的选择。不要误用不带 --staged 的 restore，它会改工作区文件。

场景 D：模型或原始录音太大，该不该 push？

本课程已忽略原始数据、缓存和模型权重，普通提交主要保存代码、配置、文档、小型结果。.gitignore 对已被跟踪的文件不会自动停止跟踪；需要移出索引时，确认后使用 git rm --cached，保留本地文件并提交。

Git LFS 是大文件管理的另一套机制，使用前要明确存储和传输方案。当前先不要把训练输出目录整体 add。

场景 E：push 报错，怎么把信息说清楚？

记录：在哪个目录、执行了哪条命令、完整错误文字，以及 git status -sb 和 git remote -v 的输出。网络、认证、历史冲突是不同问题，不要通过重新 init、删仓库或 force push 来碰运气。

你的机器曾使用本地 Clash 的 7897 端口解决连接问题；那是当时的环境事实，不保证今天代理仍然运行。需要时再检查端口与代理状态。

场景 F：Notebook 明明跑过了，为什么 GitHub 看着不对？

Notebook 文件保存代码、输出和执行编号，内核的实时变量是另一回事。修改后不重跑可能留下旧输出；重跑后不保存，Git 仍看到旧文件。运行验证、Ctrl+S、commit 和 push 都有各自的作用。

如果未来输出非常大，可以在确认实验记录另有保存后清理输出再提交；不要把“清理显示”理解为训练结果已经可复现。

用三个判断，检查是否真的分清了

点击你的答案后查看解释。这里只做本地练习，不收集、不上传你的选择。

1．我修改并保存了文件，直接 push 就会上传吗？

push 同步的是提交。先保存，再 add，再 commit，最后 push。

2．Issue 列表为 0，但 Code 页有新文件，上传成功了吗？

Issue 记录讨论和任务；文件通过提交保存在仓库。两者数量没有这种对应关系。

3．只想撤销 add，保留刚写的笔记，应选哪个？

--staged 调整暂存区，保留工作区的文字；不带它的 restore 会恢复工作文件内容。
